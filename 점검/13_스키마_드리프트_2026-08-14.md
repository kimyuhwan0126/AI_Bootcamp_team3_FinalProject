# 13 · 스키마 드리프트 확인 — 2026-08-14

배포수준 최종 점검 ①. `schema_v2.sql`(이 저장소가 정답이라고 여기는 스키마)과 운영 Neon DB 의
지금 스키마를 대조했다. **읽기만 했다** — select 만 쓰는 일회성 스크립트로
`information_schema.columns` · `pg_constraint`(`information_schema.table_constraints` 대신
`pg_get_constraintdef` 로 더 자세히 봤다) · `pg_indexes` · `information_schema.tables` 를 훑었다.
DDL 은 하나도 실행하지 않았다.

## 결과 — **확인함, 어긋난 것 없음**

`schema_v2.sql` 에 있는 표 7개(`users`·`meetings`·`participants`·`candidates`·`votes`·`geo_cache`·
`places_cache`) 를 하나씩 대조했다.

- **표**: 운영 DB 의 `public` 스키마에 있는 표는 정확히 이 7개뿐이다. 더 있지도, 빠지지도 않았다.
- **칸**: 표마다 칸 이름·타입·nullable·기본값이 파일과 전부 같았다. 특히 파일 안에 "운영 DB 에는
  있는데 파일에는 나중에 붙였다"고 적어 둔 세 칸 — `meetings.ai_used_region`·`ai_used_place`,
  `participants.going`, `geo_cache.country` — 도 실제로 다 있었고 타입·기본값도 파일과 같았다
  (이 셋은 `lib/db.ts` 의 `AI칸준비()`·`칸준비()` 가 `add column if not exists` 로 붙이는 것들이라,
  파일과 그 함수 정의가 서로 어긋나지 않았는지도 같이 확인한 셈이다).
- **제약조건**: PK·UNIQUE·CHECK·FK 전부 이름과 정의(`pg_get_constraintdef`)가 파일과 같았다.
  파일 맨 아래 "[적용 기록]" 에 적힌 F1·F2·F4·F5·C1·C7·C8(ALTER 7개로 붙였다고 적힌 것들)이
  실제로 다 붙어 있는 것도 확인했다 — 예를 들어 `meetings_host_fk` 가 `on delete no action`
  인지(`set null` 로 남아 있지 않은지), `candidates_created_by_fk` 가 `on delete set null` 인지,
  `candidates.ref_id` 가 `not null` 인지 등.
  파일이 "일부러 안 붙였다"고 적어 둔 것들(`parked_under` → `candidates` FK, `closed_at`/`stage`
  관련 CHECK 셋, `votes` 쪽 F6·F7)도 실제로 **안 붙어 있는 것**을 확인했다 — 이것도 드리프트가
  아니라 파일에 적힌 그대로다.
- **인덱스**: `pg_indexes` 로 본 인덱스 전부(PK·UNIQUE 가 자동으로 만드는 것 포함) 파일의
  `create index` 문과 이름·칼럼·부분조건(`participants_user_idx` 의
  `where user_id is not null` 포함)까지 같았다.

## 확인한 방법

`tests/_schema_drift_check.mjs` 라는 일회성 스크립트를 만들어 `.env.local` 의 `DATABASE_URL` 로
`neon()` 태그드 템플릿을 통해 세 종류를 조회하고 표로 출력해 `schema_v2.sql` 을 눈으로 대조했다.
select 문 외에는 아무것도 안 돌렸다. **감사가 끝난 뒤 이 스크립트는 지웠다** — 상시로 둘 필요가
없는 진단용 1회 도구였다.

## 결론

`schema_v2.sql` 은 지금 운영 DB 의 실제 모습과 **정확히 일치한다**. 이 파일을 "정답"으로 계속
믿고 다음 마이그레이션의 기준으로 써도 된다.
