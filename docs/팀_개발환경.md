# 팀 개발 환경 — 동시에 개발하고, 머지 충돌 없이 합치기

> 대상: 모이머를 함께 개발하는 팀원 전원
> 전제: 각자 Claude Code(또는 Ollama + GLM)로 개발한다

## 한 줄 요약

**머지 충돌은 git 문제가 아니라 파일 배치 문제다.**
두 사람이 같은 파일을 안 만지게 나눠두면 충돌은 애초에 안 난다.
아래 규칙은 전부 그 한 가지를 위한 것이다.

---

## 0. Node 버전 — `.nvmrc` 로 고정

```bash
nvm use          # .nvmrc 를 읽어 맞춰 준다 (현재 22)
node -v          # v22.x 이면 OK
```

nvm 을 안 쓴다면 **Node 22** 를 설치한다. CI 도 같은 `.nvmrc` 를 읽으므로
버전을 올릴 때 고칠 곳은 그 파일 하나다.

> "내 컴에선 되는데" 의 절반은 Node 버전 차이에서 온다.

## 0-2. 커밋 이메일 가리기 — **처음 한 번, 꼭**

이 저장소는 **공개**다. 커밋에 박힌 이메일은 누구나 API 로 수집할 수 있어
스팸·피싱 표적이 된다. 실제로 초기 커밋 9건에 개인 지메일이 그대로 남았다.

### ① GitHub 설정 (한 번만)

`GitHub → Settings → Emails`

```
☑ Keep my email addresses private
☑ Block command line pushes that expose my email
```

두 번째 항목이 중요하다 — 실수로 개인 이메일로 커밋해 push 하면 **GitHub 이 막아준다.**

### ② 내 noreply 주소 확인

같은 화면에 이런 형태로 표시된다:

```
12345678+내아이디@users.noreply.github.com
```

### ③ 로컬 git 에 적용

```bash
git config --global user.email "12345678+내아이디@users.noreply.github.com"
git config user.email          # 확인
```

> ⚠️ **이미 올라간 커밋의 이메일은 바뀌지 않는다.** 히스토리를 다시 쓰면
> 태그·PR·브랜치가 전부 어긋나므로 하지 않는다. 앞으로를 막는 것이 목적이다.

## 1. 브랜치

```
main      배포용. 항상 데모 가능해야 한다. 통합 담당자만 건드린다
 ↑
develop   통합 브랜치. 모든 PR 이 여기로 들어온다
 ↑
feat/*    개인 작업 브랜치. develop 에서 따고, 매일 develop 을 받아온다
```

```bash
git checkout develop && git pull origin develop
git checkout -b feat/weather-scoring
# ... 작업 ...
git push -u origin feat/weather-scoring
```

**매일 develop 을 받아온다.** 오래 묵힌 브랜치가 진짜 충돌의 원인이다 —
파일이 겹쳐서가 아니라 3주치 차이를 한 번에 합치려니까 터진다.

```bash
git fetch origin develop && git merge origin/develop
```

## 2. 저장소 설정 (통합 담당자가 한 번만)

GitHub 저장소 → **Settings**

### 2-1. 브랜치 보호 — `Rules` → `Rulesets`

> 사이드바에 `Branches` 메뉴도 있지만 그건 **구 방식(branch protection rules)** 이다.
> 우리는 **Rulesets** 을 쓴다 — 룰셋 하나로 여러 브랜치를 동시에 지정할 수 있다.

`Settings` → 왼쪽 **`Rules`** (화살표를 눌러 펼친다) → **`Rulesets`**
→ `New ruleset` → **`New branch ruleset`**

`main` 과 `develop` 각각 하나씩 만든다.

| 항목 | 값 |
|---|---|
| Ruleset Name | `protect-main-develop` |
| Enforcement status | **Active** ← 기본이 `Disabled` 다. 안 바꾸면 규칙이 하나도 안 걸린다 |
| Bypass list | **비워 둔다** (자기를 넣으면 우회 가능해져 의미가 없다) |
| Target branches → `Add target` **2번** | ① `Include default branch`(=main) ② `Include by pattern` → `develop` |
| Rules | ✅ Restrict deletions |
| " | ✅ Require a pull request before merging |
| " | ✅ Require status checks to pass |
| " | ✅ Block force pushes |
| ↳ Required approvals | **`0`** ⚠️ 1 이상이면 자기 PR 을 자기가 머지 못 한다. 팀원 합류 후 올린다 |
| ↳ Require review from Code Owners | **끔** ⚠️ 같은 이유. 팀원 합류 후 켠다 |
| ↳ Status checks | `verify (flags-off)` · `verify (flags-on)` (GitHub Actions) |
| ↳ Require branches to be up to date | ✅ |

> Status check 이름은 **CI 가 한 번 돌아야 목록에 뜬다.** 저장소를 막 만들었다면
> PR 을 하나 열어 CI 를 돌린 뒤에 다시 와서 체크한다.

### 2-2. 머지 방식

**세 가지(Merge · Squash · Rebase)를 모두 열어 두고, 상황에 맞게 고른다.**

| 머지 | 방식 | 왜 |
|---|---|---|
| `feat/*` → `develop` | **Squash and merge** | PR 하나가 커밋 하나로 남아 히스토리가 깔끔하다 |
| `develop` → `main` | **Create a merge commit** | Squash 로 하면 develop 커밋 전체가 한 덩어리로 뭉개지고, 그 뒤로 두 브랜치 히스토리가 갈라져 **다음 머지마다 충돌**한다 |

> ⚠️ "Squash 만 허용"으로 잠그지 않는다. `develop → main` 이 망가진다.

| 위치 | 설정 |
|---|---|
| General → Pull Requests | ✅ Automatically delete head branches (머지된 브랜치 자동 삭제) |

### 2-3. 비밀키 보호 — `Advanced Security`

`Settings` → 왼쪽 **`Advanced Security`** → 페이지 **맨 아래**
(`Code scanning` · `Copilot Autofix` · `Protection rules` 다음, 푸터 바로 위)

| 항목 | 있어야 할 상태 |
|---|---|
| **Secret Protection** (예전 이름: Secret scanning) | 켜짐 |
| **Push protection** | 켜짐 |

Push protection 이 켜져 있으면 API 키가 들어간 커밋은 **push 자체가 거부된다.**
`.gitignore` 의 `.env*.local` 은 1차 방어선일 뿐이라 둘 다 켠다.

> ⚠️ **버튼 글씨가 곧 상태가 아니다.** 버튼은 *지금 할 수 있는 행동*을 뜻한다.
> `Disable` 이라고 적혀 있으면 **이미 켜져 있다는 뜻** — 누르면 꺼진다.
> `Enable` 이면 꺼져 있으니 누른다.
>
> 공개 저장소는 GitHub 이 **기본으로 켜준다.** 대개 `Disable` 로 보일 것이고,
> 그러면 아무것도 하지 않으면 된다.

### 안 켜도 되는 것

`Dependabot`(alerts/security updates/version updates) 과 `CodeQL analysis` 는
**켜지 않는다.** 3주짜리 프로젝트에서는 자동 PR·경보 노이즈만 늘어난다.
`Copilot Autofix` 는 켜져 있어도 무해하니 그대로 둔다.

### 2-4. CODEOWNERS

`.github/CODEOWNERS` 의 `@TODO-...` 자리에 **팀원 GitHub 아이디를 채운다.**

> ⚠️ **경로에 `[code]` 를 그대로 쓰지 말 것.** CODEOWNERS 는 gitignore 문법이라
> 대괄호가 **문자 클래스**로 해석된다 — `[code]` 는 `c`·`o`·`d`·`e` 중 한 글자에
> 매칭되고 실제 폴더 `app/m/[code]/` 에는 **절대 매칭되지 않는다.**
> Next.js 동적 라우트를 가리킬 땐 `*` 를 쓴다: `/app/m/*/sections/ChatPanel.tsx`
아이디가 틀리면 GitHub 이 조용히 무시하니, 설정 후 PR 을 하나 열어
리뷰어가 자동 지정되는지 눈으로 확인할 것.

## 3. 누가 어떤 파일을 갖는가

### 🔒 공용 — 통합 담당자만 (PR 로 요청)

```
lib/types.ts          lib/store.ts        lib/persistence.ts
lib/flags.ts          lib/scoring/index.ts    lib/scoring/types.ts
app/globals.css       app/api/meeting/route.ts
db/schema.sql         package.json        CLAUDE.md
```

여러 기능이 동시에 건드리는 곳이다. 각자 고치면 머지가 지옥이 된다.
**여기를 고쳐야 할 것 같으면 멈추고 PR 설명에 이유를 쓴다.**

### ✅ 개인 — 자기 파일만

| 기능 | 파일 |
|---|---|
| 추천 알고리즘 | `lib/scoring/<내이름>.ts` 하나 (자세히는 `lib/scoring/CLAUDE.md`) |
| 날씨 | `lib/weather.ts` + `lib/scoring/weather.ts` |
| 채팅·AI 파싱 | `lib/ai.ts` · `lib/parse.ts` · `app/m/[code]/sections/ChatPanel.tsx` |
| 화면 | `app/m/[code]/sections/<자기섹션>.tsx` |

### DB 변경

`db/schema.sql` 을 고치지 않는다. `db/migrations/NNN_설명.sql` 파일을
**새로 추가**한다. 자세히는 `db/migrations/README.md`.

## 4. 기능 플래그

만드는 중인 기능은 **플래그 뒤에** 둔다. 그래야 절반만 된 상태로 develop 에
들어가도 남의 화면이 안 깨진다.

```bash
# .env.local — 커밋되지 않는다
NEXT_PUBLIC_FF_AI_CHAT=1     # 내가 개발 중인 것만 켠다
```

**상수를 직접 고치지 않는다.** (`lib/flags.ts` 참고)
브랜치마다 값이 달라지면 머지할 때마다 그 줄에서 충돌난다.

## 5. 검증 — PR 올리기 전에

```bash
npm run verify     # tsc + build + 브라우저 스모크
```

> 처음 한 번은 크로미움(~100MB)을 자동으로 받습니다(`pretest:smoke`).
> 두 번째부터는 즉시 넘어갑니다.

⚠️ **`npm run build` 통과 = 동작 아님.**
이 프로젝트에서 타입검사·빌드를 **둘 다 통과**하고도 모임 상세 화면이 통째로
안 그려진 적이 있다(`useEffect` 를 조건부 `return` 뒤에 둔 경우).
그래서 CI 가 실제로 크로미움을 띄워 핵심 경로를 클릭한다.

CI 는 플래그를 끈 상태(`flags-off`)와 켠 상태(`flags-on`) 두 번 돈다.
꺼둔 기능이 썩지 않게 하기 위해서다.

### 5-1. 눈으로 확인하기 — 실제 응답을 꺼내는 법

`npm run verify` 가 통과해도 **값이 맞는지는 확인되지 않는다.** 데이터를 바꿨으면
서버를 띄워 직접 꺼내 본다. 아래는 2026-08-06 에 실제로 동작을 확인한 절차다.

```bash
npm run build
ENABLE_DEBUG=1 npx next start -p 3100 &
```

**① 모임을 시드한다** — `/api/debug` 로 원하는 상태의 모임을 만든다.

```bash
curl -s localhost:3100/api/debug                    # 시나리오 목록
curl -s -X POST localhost:3100/api/debug \
  -H 'content-type: application/json' \
  -d '{"scenario":"chat_region_done"}'              # → {"ok":true,"code":"4GQX5Y",...}
```

> `ENABLE_DEBUG=1` 이 없으면 **운영 빌드에서 403** 이다(`app/api/debug/route.ts`).
> 값이 아니라 존재만 보면 `ENABLE_DEBUG=0` 으로도 잠금이 풀리므로 `!== "1"` 로 검사한다.

**② 코드로 조회한다.**

```bash
curl -s "localhost:3100/api/meeting?code=4GQX5Y"
```

> ⚠️ **`?action=…` 은 GET 에 없다.** 이 라우트의 GET 은 `code` 만 받는다
> (`app/api/meeting/route.ts`). `?action=places&region=…` 같은 건 **빈 응답**이 온다 —
> 값이 0 이라서가 아니라 애초에 아무것도 안 돌려준 것이라, 검증했다고 착각하기 쉽다.

**③ 화면도 본다.** 응답이 맞아도 화면이 그걸 어떻게 그리는지는 별개다.
`http://localhost:3100/m/{코드}` 를 열어 눈으로 확인한다.

**④ 서버를 끈다.**

```bash
ps aux | grep "[n]ext-server" | awk '{print $2}' | xargs -r kill -9
```

> ⚠️ **`pkill -f "next start"` 를 쓰지 마라 — 자기 셸까지 죽는다**(여러 번 겪음).
> 그리고 프로세스 이름은 `next start` 가 아니라 **`next-server`** 다.
> `grep "next start"` 로는 **안 잡히는데 조용히 0건이라** 정리된 줄 알고 넘어가게 된다.
> `[n]ext-server` 의 대괄호는 grep 자신이 잡히지 않게 하는 관용구다.

## 6. Vercel Preview — 이게 협업 효과가 제일 크다

PR 을 올리면 **그 PR 전용 URL** 이 자동으로 생긴다.
팀원이 코드를 받지 않고 **자기 폰으로 바로 눌러볼 수 있다.**

- vercel.com → Project → Settings → Git → 저장소 연결
- Environment Variables 는 Production / Preview 를 나눠 넣는다
- ⚠️ `DATABASE_URL` 은 **Production 만**.
  Preview 에는 별도 테스트 프로젝트(브랜치 DB) 값을 쓰거나 비워둔다(비우면 인메모리로 돈다)

## 7. AI 로 개발할 때 (Claude Code · Ollama+GLM 공통)

- **각 폴더의 `CLAUDE.md` 를 먼저 읽힌다.** 루트 하나로는 부족하다 —
  특히 GLM 처럼 컨텍스트가 짧은 모델은 긴 전역 지시의 뒷부분을 흘린다.
  현재 있는 것: 루트 `CLAUDE.md`, `lib/scoring/CLAUDE.md`, `app/m/[code]/CLAUDE.md`
- **한 파일 400줄을 넘기지 않는다.** 큰 파일에서는 AI 가 엉뚱한 곳을 고친다.
  넘으면 쪼갠다.
- **AI 가 만든 코드는 반드시 브라우저로 열어본다.** 타입검사만 믿지 않는다.
- PR 본문에 `🤖 Generated with Claude Code` 표기 (루트 `CLAUDE.md` §5)
