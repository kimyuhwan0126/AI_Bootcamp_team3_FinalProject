# ODsay 프록시(Cloudflare Tunnel) 시도 기록 — 실패 후 보류

_작성: 2026-08-04 · 통합·머지 세션 2 · 대상: 멘토님 검토용_

> **여기 적힌 값은 전부 실측이다. 확인하지 못한 것은 "미확인"이라고 적었다.**
> 원인을 끝내 특정하지 못했고, 그 사실 자체를 숨기지 않았다.

---

## 0. 한 줄 요약

배포 환경(Vercel)에서 **ODsay 대중교통 API 를 쓰지 못한다.** IP 화이트리스트 때문이다.
노트북을 고정 IP 프록시로 세우고 Cloudflare Tunnel 로 노출하는 우회로를 만들었으나
**종단 검증에 실패**했고, 발표 일정을 고려해 **보류**했다.

**지금 서비스는 정상 동작한다** — 대중교통 시간이 거리 추정값일 뿐이고, 화면이 그
사실을 "거리 추정으로 계산"이라고 밝힌다.

---

## 1. 문제 — 왜 배포에서 ODsay 를 못 쓰나

ODsay 서버 키는 **호출하는 서버의 공인 IP 를 화이트리스트에 등록**해야 통한다.

그런데 **Vercel 서버리스는 나가는 IP 가 요청마다 달라진다.** 등록할 IP 자체가 없다.

| 환경 | ODsay 호출 | 결과 |
|---|---|---|
| 팀원 로컬 (`npm run dev`) | 집·사무실 IP 등록하면 됨 | ✅ 동작 (실측) |
| **Vercel 배포** | 나가는 IP 가 유동 | ❌ **등록 불가** |

그래서 프로덕션은 ODsay 키 없이(`odsay: false`) 돌고 있고, 대중교통 이동시간이
**전부 거리 기반 추정값**이다.

> 참고로 이건 ODsay 의 결함이 아니라 **서버 키의 표준적인 보안 모델**이다.
> 문제는 우리가 IP 가 고정되지 않는 플랫폼에 올렸다는 데 있다.

---

## 2. 시도한 해결책 — 고정 IP 프록시 + Cloudflare Tunnel

```
[Vercel 함수]  ──HTTPS──▶  [Cloudflare Quick Tunnel]  ──▶  [노트북의 프록시]  ──▶  [ODsay]
   IP 유동                   *.trycloudflare.com              공인 IP 고정          ↑
                                                                            여기만 화이트리스트에 등록
```

**핵심 아이디어**: ODsay 에 찍히는 IP 를 **노트북 IP 하나로 고정**한다.
Cloudflare Quick Tunnel 은 노트북에 공인 주소를 붙여 주는 무료 터널이다.

### 구현 (PR #28 — 머지 완료)

| 환경변수 | 역할 |
|---|---|
| `ODSAY_BASE_URL` | ODsay 대신 호출할 주소(= 터널). **비면 `api.odsay.com` 직접 호출** |
| `ODSAY_PROXY_SECRET` | 프록시가 요구하면 `x-proxy-secret` 헤더로 전송. **비면 헤더 없음** |

> **설계 원칙**: 환경변수가 비어 있으면 **기존과 100% 동일하게 동작**한다.
> 팀원 로컬은 이 값을 넣지 않으므로 아무 영향이 없다.

같은 PR 에서 **`live` 판정도 함께 고쳤다.** 이게 나중에 결정적으로 중요해진다:

| | 이전 | 이후 |
|---|---|---|
| 판정 기준 | **키가 있는가** | **실제로 API 값을 받았는가** |
| 프록시 장애 시 | "실 이동시간 기준"이라고 **거짓 표시** | "거리 추정으로 계산"으로 **정직 표시** |

---

## 3. 검증 시도 — 무엇을 했고 어떻게 실패했나

**프로덕션이 아니라 Preview 배포에서** 검증했다. 발표를 앞둔 프로덕션을 실험대로
쓰지 않기 위해서다.

### 시도 1

| 단계 | 결과 |
|---|---|
| 노트북에서 프록시 + Cloudflare Tunnel 기동 | ✅ |
| Vercel 환경변수 3개 투입 후 재배포 | ✅ |
| `/api/status` 확인 | `odsay: true` · `odsayProxy: true` · `odsayProxyAuth: false` ✅ |
| **추천 실행** | ❌ **"거리 추정으로 계산"** (`live: false`) |
| Vercel 로그에서 원인 확인 | ❌ **`Warning 0 · Error 0`** — 로그가 아예 없음 |

**원인을 한 칸도 좁히지 못했다.**

### 중간에 발견한 것 — 우리 코드가 실패를 삼키고 있었다

로그가 없는 이유를 코드에서 찾았다. `lib/odsay.ts` 가 실패를 **조용히 버리고** 있었다:

```ts
if (!r.ok) return null;      // 5곳 — 프록시 401/403, Cloudflare 502/1033 이 여기로 사라짐
catch { return null }         // 3곳 — 터널이 죽어 fetch 가 던져도 로그 없음
```

`console.warn` 은 **"ODsay 가 HTTP 200 으로 에러 본문을 준 경우"에만** 찍히고 있었다.
PR #28 이 "로그로 터널 장애와 키 문제를 구분한다"고 했지만 **실제로는 구분이 안 됐다.**

→ **PR #29 로 실패 8곳 전부에 사유 로그를 넣었다.**
   (⚠️ URL 에 `apiKey` 가 들어 있어 **호스트만** 로그에 싣는다)

동시에 `/api/status` 에 **배포 신원**(`deploy.env`·`branch`·`commit`)을 추가했다.
Preview 와 Production 응답이 **글자 하나 다르지 않아** 어느 배포를 보고 있는지
확정할 수 없었기 때문이다 — 이것 때문에도 한 라운드를 헛돌았다.

### 시도 2 (로그 개선 후)

| 단계 | 결과 |
|---|---|
| 새 빌드 확인 (`deploy.commit` 대조) | ✅ |
| 추천 재실행 | ❌ **여전히 "거리 추정으로 계산"** |

### 판정을 도운 결정적 대조

키가 **없는** 로컬 빌드로 같은 좌표를 돌렸더니 **`최대 18분 · 편차 12분`** 이 나왔다.
Preview 결과와 **숫자가 정확히 같았다.**

> **→ Preview 는 ODsay 를 한 번도 타지 못했다.** 부분 성공이 아니라 전부 폴백이었다.

## 4. 원인 — 후보 3개로 좁혔으나 특정 실패

| 후보 | 근거 | 확인 방법 | 상태 |
|---|---|---|---|
| ① **Vercel 의 `ODSAY_BASE_URL` 이 옛 터널 주소** | Quick Tunnel 주소는 **재시작할 때마다 바뀐다** | 지금 터널 주소와 Vercel 값 대조 | **미확인** |
| ② **프록시가 공유 비밀을 요구하는데 우리가 안 보냄** | `/api/status` 가 `odsayProxyAuth: false` | 프록시 코드에서 `x-proxy-secret` 검사 여부 확인 (💰 0콜) | **미확인** |
| ③ **노트북 공인 IP 가 ODsay 화이트리스트에 미등록** | 프록시를 거치면 ODsay 에는 **Vercel 이 아니라 노트북 IP** 가 찍힌다 | `curl ifconfig.me` → ODsay 콘솔 대조 | **미확인** |

**②가 가장 빨리 확인된다** — 프록시 코드를 한 번 읽으면 되고 API 호출이 0건이다.

> 세 후보를 끝까지 좁히지 못한 채 보류했다. **"원인 미상"이 현재의 정확한 상태다.**

---

## 5. 왜 관뒀나 — 판단 근거

### ① 발표 환경에서 신뢰할 수 없는 구조다

이게 가장 큰 이유다. 이 우회로는 **노트북이 켜져 있고 터널이 살아 있어야만** 동작한다.

| 상황 | 결과 |
|---|---|
| 노트북 절전·종료 | 배포된 서비스의 대중교통 시간이 **조용히 추정값으로 떨어짐** |
| Wi-Fi 변경·재접속 | 공인 IP 변경 → **화이트리스트 불일치** |
| 터널 재시작 | **주소가 바뀜** → Vercel 환경변수 수정 + 재배포 필요 |

**발표 중에 노트북을 닫으면 서비스 품질이 바뀐다.** 시연용으로도 위험하다.

### ② 지금도 서비스는 정상 동작한다

ODsay 없이도 전체 플로우가 돌고, **화면이 추정값임을 정직하게 밝힌다**(PR #28).
"가짜를 실제인 것처럼 그리지 않는다"는 프로젝트 원칙이 지켜지는 상태다.

### ③ 남은 시간을 다른 곳에 쓰는 게 낫다고 판단했다

원인 후보가 3개 남아 있고 각각 다른 담당자(프록시·ODsay 콘솔·Vercel)의 손이 필요했다.
투입 대비 회수가 불확실했다.

## 6. 실패했지만 남은 것

이 시도 과정에서 **서비스에 실제로 남은 개선**이 있다. 헛수고는 아니었다.

| 얻은 것 | 내용 |
|---|---|
| **정직한 `live` 판정** (#28) | 프로덕션에서 **추정 894분을 "실 이동시간"이라 표시하던 버그**가 이 작업 중에 드러나 고쳐졌다 |
| **장애 진단 능력** (#29) | 조용히 사라지던 실패 8곳에 사유 로그. 다음 시도는 원인이 로그에 바로 남는다 |
| **배포 신원** (#29) | `/api/status` 로 Preview/Production 을 구분할 수 있게 됐다 |
| **환경변수 함정 문서화** | "환경변수는 **넣는 시점이 아니라 배포 시점에** 적용된다" — 이걸 몰라 프로덕션에 의도치 않게 키가 들어간 것을 릴리스 때 발견했다 |
| **릴리스 `v0.2.0`** | 위 수정들이 묶여 배포됐다 (철도 매핑 · 요금 오표시 · 전국 거점 · 디버그 잠금 버그 포함) |

**💰 비용**: 검증 시도로 소모한 ODsay 콜은 **사실상 0건**이다. 요청이 ODsay 에
도달하지 못했기 때문이다(무료 한도 1,000콜/일).

## 7. 🙏 멘토님께 여쭙고 싶은 것

**"IP 가 고정되지 않는 서버리스에서, IP 화이트리스트 기반 API 를 어떻게 쓰는가"** 가
문제의 본질입니다. 저희가 생각한 선택지는 다음과 같은데, 실무에서 어떤 쪽을 택하는지
조언을 구하고 싶습니다.

| 방안 | 장점 | 걱정되는 점 |
|---|---|---|
| **A. 소형 VPS 를 프록시로** | 고정 IP · 24시간 · 노트북 의존 없음 | 월 비용 · 운영 부담 |
| **B. Vercel 고정 IP 기능** | 구조 변경 없음 | **유료 플랜** 필요 |
| **C. ODsay 웹키로 전환**(브라우저 직접 호출) | 서버 IP 문제 자체가 사라짐 | 키가 **브라우저에 노출** · Referer 기반 제한의 실효성 |
| **D. 지금처럼 추정값 유지** | 비용 0 · 이미 정직하게 표시됨 | 이동시간 정확도가 낮음(체감 8~14배 과대 구간 존재) |

부차적으로 여쭙고 싶은 것:

1. **터널 방식(현재 시도)을 발표용으로라도 쓸 만한가**, 아니면 구조적으로 부적합한가
2. 원인 후보 3개 중 **어디부터 보는 것이 효율적인가**
3. 실패한 우회로의 코드(`ODSAY_BASE_URL` 경유 경로)를 **남겨둘지 걷어낼지**
   — 현재는 환경변수가 비면 무해하므로 남겨 뒀습니다

## 8. 재개한다면 — 확정된 절차

보류를 푸는 경우를 대비해 순서를 정해 뒀다. **순서를 지키지 않으면 프로덕션이 나빠진다.**

1. **터널을 먼저 기동**해 새 주소를 확보 (주소는 재시작마다 바뀐다)
2. 환경변수를 **Preview 스코프에만** 넣고 재배포
3. Preview 에서 종단 확인
   - ⚠️ **반증 테스트는 반드시 "새 좌표"로.** `routeCache` 에 TTL 이 없어 **이미 캐시된
     좌표쌍은 터널이 죽어도 `live: true`** 로 나온다 — 같은 좌표로 하면 오판한다
4. 통과한 뒤에야 Production 스코프에 추가 + 재배포

### 재개 전에 먼저 고칠 것 🔴

**`/api/diag` 의 ODsay 항목이 프록시를 타지 않는다.** 주소가 `api.odsay.com` 으로
하드코딩돼 있어(`app/api/diag/route.ts:99`), **프록시가 완벽히 동작해도 실패로 뜬다.**
진단 도구가 오진을 만드는 상태라, 이걸 먼저 고쳐야 한다.

### 저장소에 없는 것 ⚠️

**프록시 구현이 저장소에 없다.** 팀원 노트북에만 있어 아무도 재현할 수 없고, 노트북이
꺼지면 배포된 서비스가 조용히 추정값으로 떨어진다. 재개한다면 `tools/odsay-proxy/` 로
실행 방법과 함께 올려야 한다.
