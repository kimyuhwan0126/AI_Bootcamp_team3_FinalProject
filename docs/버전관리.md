# 버전 관리 규칙

> 최종 발표일에 **v1.0.0** 이 되도록 설계했다.
> 일반적인 소프트웨어 릴리스 관례(SemVer)를 그대로 따른다.

## 왜 v8 에서 0.1.0 으로 "내려가나"

숫자가 줄어드는 게 아니라 **의미가 다른 숫자**로 바뀌는 것이다.

| | 예전 (`Moimer` 저장소) | 새 저장소 |
|---|---|---|
| v8 의 뜻 | **8번째로 다시 만든 시제품** | — |
| 0.1.0 의 뜻 | — | **아직 정식 출시 전인 개발 버전** |

SemVer 규칙에 `0.y.z` 는 **"초기 개발 중 · 언제든 바뀔 수 있음"** 이라는 뜻이 명시돼 있고,
`1.0.0` 은 **"처음으로 외부에 내놓는 안정 버전"** 이다.
그래서 발표일 = 1.0.0 이 정확한 사용법이다.

> 새 저장소 `0.1.0` 의 코드는 옛 저장소 `v8.1.0` 과 같다.
> 혼동을 막기 위해 `CHANGELOG.md` 맨 위에 이 대응을 적어 둔다.

## 버전 번호 읽는 법 — `MAJOR.MINOR.PATCH`

| 자리 | 언제 올리나 | 예 |
|---|---|---|
| **MAJOR** | 정식 출시 / 되돌릴 수 없는 큰 변화 | 발표일 `1.0.0` **딱 한 번** |
| **MINOR** | 기능 추가 (기존 것은 그대로 동작) | `0.2.0` → `0.3.0` |
| **PATCH** | 버그 수정만 | `0.3.0` → `0.3.1` |

**커밋 접두사가 곧 버전 규칙이다.** (Conventional Commits)

| 접두사 | 뜻 | 버전 영향 |
|---|---|---|
| `feat:` | 기능 추가 | MINOR |
| `fix:` | 버그 수정 | PATCH |
| `refactor:` | 동작 그대로, 구조만 | 없음 |
| `docs:` `test:` `chore:` | 문서 · 테스트 · 잡일 | 없음 |

## 3주 릴리스 계획

| 버전 | 내용 | 시점 |
|---|---|---|
| `0.1.0` | 통합 개발 환경 세팅 (CI · 소유권 · 플래그 · PWA) | 1주차 초 |
| `0.2.0` | 화면 분할 완료 · 팀원 브랜치 착수 | 1주차 |
| `0.3.0` | 추천 알고리즘 1차 (스코어러 2개 이상) | 2주차 |
| `0.4.0` | 채팅 · AI 파싱 | 2주차 |
| `0.5.0` | 날씨 · 개인별 선호 | 3주차 초 |
| `0.9.0-rc.1` | **기능 동결.** 이후 버그 수정만 | 발표 3일 전 |
| **`1.0.0`** | **최종 발표** | 발표일 |

`0.9.0-rc.1` 의 `rc` 는 release candidate(출시 후보) — "이대로 낼 생각인데 마지막 점검 중"

## 올리는 방법 (통합 담당자만)

버전 올리기는 `package.json` 을 건드리므로 통합 담당자 몫이다 (`.github/CODEOWNERS`).

```bash
git checkout main && git pull origin main

npm version minor -m "chore(release): v%s"   # 0.2.0 → 0.3.0
# npm version patch  → 0.3.0 → 0.3.1
# npm version 1.0.0  → 정확한 번호 지정

git push origin main --follow-tags
```

`npm version` 이 `package.json` 수정 + 커밋 + 태그를 한 번에 한다.
그다음 GitHub → Releases → Draft a new release 에서 그 태그를 골라
`CHANGELOG.md` 의 해당 절을 붙여넣고 발행한다.

## 규칙 4개

1. **버전은 `main` 에서만 올린다.** `develop`·`feat/*` 에서 올리지 않는다.
2. **`CHANGELOG.md` 를 먼저 쓰고 버전을 올린다.** 기록 없는 릴리스 금지.
3. **`1.0.0` 은 발표일에 딱 한 번.** 그전에 실수로 올리지 않는다.
4. **태그를 지우지 않는다.** 잘못 냈으면 다음 번호로 새로 낸다
   (이미 받아간 사람의 버전과 내용이 달라지는 게 더 위험하다).

## 새 저장소 첫 세팅 (이관 절차)

```bash
# 1) 지금 코드 그대로 새 저장소로
git clone <옛 저장소> moimer-new && cd moimer-new
git remote set-url origin https://github.com/<owner>/<새저장소>.git

# 2) 히스토리를 새로 시작 (옛 v1~v8 반복 이력은 참고용으로만 남긴다)
rm -rf .git && git init -b main

# 3) 버전 초기화
npm version 0.1.0 --no-git-tag-version --allow-same-version

# 4) 첫 커밋
git add -A
git commit -m "feat: 모이머 통합 개발 환경 (구 v8.1.0 코드베이스)"
git push -u origin main
git tag v0.1.0 && git push origin v0.1.0

# 5) develop 분기
git checkout -b develop && git push -u origin develop
```

이후 저장소 보호 설정은 `docs/팀_개발환경.md` §2.
