## 1. 왜 이 세팅을 하게 되었나

### 문제의식

지금까지는 한 명이 만들고 나머지가 보는 방식이었습니다. 앞으로 3주는 4명이 각자
다른 기능(추천 알고리즘 · 채팅/AI 파싱 · 날씨 · 개인별 선호)을 **동시에** 만들어야 합니다.

여기서 프로젝트가 망하는 방식은 대부분 정해져 있습니다.

> **"각자 잘 만들었는데 합칠 수가 없다."**

그래서 기능을 만들기 전에, **합쳐지는 구조**부터 만들었습니다.

### 근거 — 지금 코드에서 실제로 확인된 문제 4가지

말이 아니라 코드에서 확인한 것들입니다.

| # | 발견한 것 | 왜 위험한가 |
|---|---|---|
| 1 | 모임 상세 화면 하나가 **1,802줄** | 두 사람이 만지면 매일 충돌. AI(특히 컨텍스트가 짧은 GLM)가 엉뚱한 곳을 고침 |
| 2 | 추천 점수식이 **두 파일에 복제** (`geo.ts`, `routing.ts`) | 한쪽만 고치는 사고. 알고리즘 담당 3명이 전부 같은 줄에서 충돌 |
| 3 | 기능 on/off 가 **코드 안의 상수** (`const AI_CHAT_ENABLED = false`) | 브랜치마다 값이 달라져 머지할 때마다 충돌. 개발하려고 켠 걸 커밋하면 남의 화면까지 켜짐 |
| 4 | **빌드가 통과했는데 화면이 통째로 안 그려진 사고** | `npx tsc` 와 `npm run build` 를 **둘 다 통과**했는데 아무것도 안 나왔음 (React 훅을 조건부 `return` 뒤에 둔 경우). 사람 눈 검사로는 못 막음 |

특히 4번이 결정적이었습니다. **"빌드 통과 = 동작"이 아니라는 걸 직접 겪었기 때문에**,
CI 에 실제 브라우저를 띄우는 테스트를 넣었습니다.

### 검증 — 그 CI 가 정말 잡는지 확인

일부러 화면을 깨뜨리고 돌려봤습니다.

```
✓ Compiled successfully                    ← 빌드는 통과
✘ 모임 생성 → 출발지 → 거점 투표 → 확정     ← 브라우저 테스트만 실패
```

의도한 대로 동작합니다.

## 2. 세팅 환경 — 무엇을 만들었나

### 2-1. 파일 소유권 분리

> **머지 충돌은 git 문제가 아니라 파일 배치 문제입니다.**
> 두 사람이 같은 파일을 안 만지게 나눠두면 충돌은 애초에 나지 않습니다.

**추천 알고리즘** — 관점 하나 = 파일 하나 = 담당자 한 명

```
lib/scoring/
  types.ts        계약(인터페이스)      🔒 통합 담당자
  index.ts        등록소               🔒 통합 담당자 (추가는 배열에 한 줄)
  fairness.ts     공평성               👤 담당자 A   ← 현재 이것만 존재
  commercial.ts   상권 밀집도           👤 담당자 B   ← 앞으로 만들 파일
  weather.ts      날씨 조건            👤 담당자 C   ← 앞으로 만들 파일
  personal.ts     개인별 선호           👤 담당자 D   ← 앞으로 만들 파일
```

새 관점을 추가할 때 하는 일은 **파일 하나 만들기 + 배열에 한 줄 추가**가 전부입니다.
한 줄 추가는 두 사람이 동시에 해도 "양쪽 다 남기기"로 끝납니다.

**모임 상세 화면** — 1,802줄 → 905줄 (담당자별 15파일로 분리)

```
app/m/[code]/sections/
  VoteList.tsx         투표 목록            👤 투표·추천 담당
  AddRegionModal.tsx   ＋ 다른 후보 등록     👤 투표·추천 담당
  ManualPickModal.tsx  ✍ 다른 후보로 확정    👤 투표·추천 담당
  ChatPanel.tsx        AI 채팅              👤 채팅·AI 파싱 담당
  TravelTimes / PastStepView / AddParticipant
```

**DB 스키마** — 파일 수정이 아니라 파일 추가로

```
db/migrations/001_xxx.sql   ← 각자 새 파일을 만든다
```

### 2-2. 기능 플래그

만드는 중인 기능은 **플래그 뒤에** 둡니다. 절반만 된 상태로 합쳐져도 남의 화면이 안 깨집니다.

```bash
# .env.local — 커밋되지 않는 개인 파일
NEXT_PUBLIC_FF_AI_CHAT=1     # 내가 개발 중인 것만 켠다
```

코드를 고치지 않고 켜기 때문에 **브랜치마다 값이 달라지지 않습니다.**

### 2-3. CI — 사람 리뷰 전에 기계가 먼저

PR 을 올리면 자동으로 돕니다.

| 검사 | 무엇을 |
|---|---|
| `npx tsc --noEmit` | 타입 오류 |
| `npm run build` | 빌드 오류 |
| **Playwright 스모크** | **실제 크로미움을 띄워** 생성 → 출발지 → 투표 → 확정을 클릭 |

그리고 **플래그를 끈 상태와 켠 상태 두 번** 돕니다.
안 돌려보는 기능은 "언제든 켤 수 있는 코드"가 아니라 "켤 수 있어 보이는 죽은 코드"이기 때문입니다.

### 2-4. AI 개발 환경 (팀원마다 다른 모델)

팀원들은 Claude Code 를 쓰지만, 일부는 Ollama + GLM 으로 붙습니다.
**모델 성능 차이를 구조로 흡수**했습니다.

| 대응 | 이유 |
|---|---|
| 폴더마다 `CLAUDE.md` 를 둔다 | 컨텍스트가 짧은 모델은 긴 전역 지시의 뒷부분을 흘림. 가까이 있는 짧은 지시가 더 잘 지켜짐 |
| 한 파일 400줄 상한 | 큰 파일에서는 AI 가 엉뚱한 곳을 고침 |
| CI 가 리뷰를 대신함 | 약한 모델은 "타입만 통과하는 코드"를 더 자주 냄 |

현재 있는 지시서: 루트 `CLAUDE.md` · `lib/scoring/CLAUDE.md` · `app/m/[code]/CLAUDE.md`

### 2-5. 안드로이드 앱 — PWA + TWA

발표 목표가 **팀원 폰에 설치된 앱**이라, 방법을 검토했습니다.

| 방식 | 코드 재작성 | 기간 |
|---|---|---|
| **PWA + TWA (채택)** | **없음** — 지금 웹앱이 그대로 앱이 됨 | 하루 |
| Flutter / React Native | 프론트엔드 전체 | 3주+ |

TWA(Trusted Web Activity)는 안드로이드 껍데기가 우리 웹앱을 브라우저 UI 없이
전체화면으로 여는 방식입니다. 사용자 눈에는 그냥 앱입니다.
Bubblewrap 으로 APK 를 만들어 **플레이스토어 없이 직접 설치**할 수 있습니다.

이미 만든 것: 매니페스트 · 서비스 워커 · 앱 아이콘 4종
남은 것: Vercel 배포(HTTPS) → Bubblewrap 실행

## 3. 세팅 방법 — 팀원이 따라 하는 절차

### 3-1. 처음 한 번

```bash
git clone https://github.com/<owner>/<저장소>.git
cd <저장소>
npm install
cp .env.example .env.local     # 값은 비워도 됨 (mock 으로 전체 동작)
npm run dev                    # http://localhost:3000
```

> **키가 하나도 없어도 전체 기능이 돕니다.** 외부 API 는 전부 mock 폴백이 있습니다.
> 실제 키를 넣을 사람만 `.env.local` 을 채웁니다. 이 파일은 **절대 커밋되지 않습니다.**

### 3-2. 커밋 이메일 가리기 (처음 한 번, 전원)

저장소가 **공개**라 커밋에 박힌 이메일은 누구나 수집할 수 있습니다.

`GitHub → Settings → Emails` 에서 두 개를 켭니다:

- ☑ Keep my email addresses private
- ☑ Block command line pushes that expose my email

그리고 같은 화면의 noreply 주소를 로컬에 적용합니다:

```bash
git config --global user.email "12345678+내아이디@users.noreply.github.com"
```

> 이미 올라간 커밋은 바뀌지 않습니다. 히스토리 재작성은 태그·PR·브랜치를
> 전부 어긋나게 하므로 하지 않고, **앞으로를 막는 것**이 목적입니다.

### 3-3. 작업할 때

```bash
git checkout develop && git pull origin develop
git checkout -b feat/weather-scoring      # 내 기능 브랜치

# ... 작업 ...

npm run verify                            # 타입 + 빌드 + 브라우저 테스트
git push -u origin feat/weather-scoring
```

GitHub 에서 `develop` 으로 PR 을 엽니다. **매일 `develop` 을 받아옵니다** —
오래 묵힌 브랜치가 진짜 충돌의 원인입니다.

### 3-4. 지켜야 할 것

- [ ] **자기 담당 파일만 만진다.** 공용 파일을 고쳐야 하면 멈추고 PR 설명에 이유를 쓴다
- [ ] **한 파일 400줄을 넘기지 않는다.** 넘으면 쪼갠다
- [ ] **만드는 중인 기능은 플래그 뒤에** 둔다
- [ ] **DB 변경은 `migrations/` 에 새 파일**로 (기존 `schema.sql` 수정 금지)
- [ ] **AI 가 만든 코드는 반드시 브라우저로 열어본다** (타입검사만 믿지 않는다)
- [ ] 커밋 접두사: `feat:` `fix:` `refactor:` `docs:` `test:` `chore:`

### 3-5. 저장소 설정 (통합 담당자가 한 번만)

GitHub → Settings

| 위치 | 설정 |
|---|---|
| **Rules → Rulesets** → New branch ruleset (`main`, `develop`) | Require a pull request before merging |
| " | Require status checks — `verify (flags-off)`, `verify (flags-on)` |
| " | Block force pushes · Restrict deletions |
| " | ⚠️ `Required approvals` 는 **0**, `Require review from Code Owners` 는 **끔** — 팀원 합류 전에는 자기 PR 을 자기가 머지 못 하게 됩니다. 합류 후 켭니다 |
| **Advanced Security** (페이지 맨 아래) | **Secret Protection + Push protection** 켜짐 확인 |
| General → Pull Requests | 머지 후 브랜치 자동 삭제 (머지 방식은 셋 다 열어 둠) |

> ⚠️ 사이드바에 `Branches` 항목이 없습니다 — 최신 UI 에서 **`Rules`** 안으로
> 들어갔습니다. Ruleset 을 만든 뒤 **Enforcement status 를 `Active`** 로 바꿔야
> 실제로 적용됩니다.
>
> **머지 방식**: `feat/* → develop` 은 **Squash and merge**, `develop → main` 은
> **Create a merge commit**. Squash 로만 잠그면 `develop → main` 에서 히스토리가
> 갈라져 이후 머지마다 충돌합니다.

> ⚠️ 보안 항목의 버튼은 *상태*가 아니라 *지금 할 수 있는 행동*입니다.
> `Disable` 로 보이면 **이미 켜져 있다**는 뜻이니 누르지 않습니다.
> 공개 저장소는 GitHub 이 기본으로 켜주므로 대개 확인만 하면 됩니다.

> 저장소를 **공개(Public)** 로 만든 이유: GitHub Free 플랜에서 **비공개 저장소는
> 브랜치 보호를 걸 수 없습니다.** 위 강제 장치가 전부 그것에 달려 있습니다.
> 대신 공개라서 키 유출 위험이 있으므로 Push protection 을 함께 켭니다.

## 4. 버전 관리 규칙

### 왜 v8 에서 0.1.0 으로 "내려가나"

숫자가 줄어드는 게 아니라 **의미가 다른 숫자**로 바뀝니다.

- 예전 `v8` = **8번째로 다시 만든 시제품** (내부 반복 횟수)
- 새 `0.1.0` = **아직 정식 출시 전인 개발 버전** (SemVer 표준 의미)

SemVer 규칙에 `0.y.z` 는 "초기 개발 중", `1.0.0` 은 "처음 내놓는 안정 버전"으로
정의돼 있습니다. 그래서 **발표일 = v1.0.0** 이 정확한 사용법입니다.

### 번호 읽는 법

| 자리 | 언제 올리나 |
|---|---|
| **MAJOR** (`1`.0.0) | 정식 출시 — **발표일에 딱 한 번** |
| **MINOR** (0.`2`.0) | 기능 추가 |
| **PATCH** (0.2.`1`) | 버그 수정만 |

### 3주 릴리스 계획

| 버전 | 내용 | 시점 |
|---|---|---|
| `0.1.0` | 통합 개발 환경 세팅 | 1주차 초 |
| `0.2.0` | 화면 분할 완료 · 팀원 브랜치 착수 | 1주차 |
| `0.3.0` | 추천 알고리즘 1차 | 2주차 |
| `0.4.0` | 채팅 · AI 파싱 | 2주차 |
| `0.5.0` | 날씨 · 개인별 선호 | 3주차 초 |
| `0.9.0-rc.1` | **기능 동결** (이후 버그 수정만) | 발표 3일 전 |
| **`1.0.0`** | **최종 발표** | 발표일 |

## 5. 발표 대비

- **발표 3일 전 기능 동결.** 이후엔 버그 수정만
- **데모 경로는 매일 초록이어야 합니다**:
  `설치 → 모임 생성 → 참여 → 출발지 → 중간지점 → 거점 투표 → 확정`
  이것이 CI 의 스모크 테스트입니다. 여기가 빨간 채로 하루를 넘기지 않습니다
- **APK 는 최소 1주 전에 한 번 끝까지 뽑아봅니다.** 발표 당일에 처음 시도하지 않습니다

## 6. 멘토님께 여쭙고 싶은 것

### ① DB — ✅ 결정됨: Neon 으로 이전 (멘토님 추천 수용)

~~Supabase 유지 vs Neon 이전~~ → **팀 결정: Neon 확정.** 저장 계층(`lib/persistence.ts`)이
격리돼 있어 드라이버·스키마 교체로 마무리했습니다 (`db/schema.sql` · `DATABASE_URL`).

남은 트레이드오프 하나는 기록해 둡니다: Neon 에는 Realtime 이 없어, 앱 안 채팅을
실제로 만들 경우 **WebSocket/SSE 서버를 직접 구축·배포**해야 합니다
(현재 채팅은 기본 비활성 + 1.8초 폴링이라 당장 영향 없음).

### ② 앱 안 채팅을 정말 만들 것인가

현재 기획서에는 *"대화는 카카오톡에서 하고, 모이머는 장소만 담당한다"* 라고 적혀 있는데,
팀 내 의견이 갈립니다. 만들어보고 발표에서 뺄 수도 있다고 보는데,
포지셔닝이 흔들리지 않을지 판단을 여쭙고 싶습니다.

### ③ 추천 알고리즘의 가중치

구조는 만들었지만 **무엇을 얼마나 반영할지**는 아직 정하지 못했습니다.
현재 점수식은 `최대 이동시간 + 편차 × 0.8` 이 전부라
상권 · 환승 · 요금 · 모임 성격이 전혀 반영되지 않습니다.

특히 **수도권 밖**에서 문제가 큽니다 — 서울↔부산이면 `김천시 개령면 신룡리` 같은
"모일 수 없는 곳"이 나옵니다. 역·터미널 기준으로 후보를 뽑는 방향을 생각 중입니다.
