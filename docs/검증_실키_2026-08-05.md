#### A-2. 한 구간만 실패할 때 화면이 어떻게 되는가 → **이게 진짜 위험이었다**

참가자 4명 중 한 명을 **자월도(옹진군, `37.2508, 126.3053`)** 로 넣었다.
ODsay 가 이 좌표를 못 푼다는 것을 먼저 1콜로 확인했다 —

로컬 실키 · `action=regions` 실측:

```

                └── ODsay 실값 ──┘        └ 직선거리 추정 ┘

그런데 모임 상세 화면은:

```
유환   ~ 가까움   실시간   31분          ← ODsay 실값
지훈   ~ 멀어요   실시간   1시간 7분      ← ODsay 실값
서연   ~ 가까움   실시간   29분          ← ODsay 실값
민준   ~ 멀어요   실시간   4시간 48분     ← 🔴 직선거리 추정인데 `실시간`
```

**한 목록 안에 실값과 추정이 섞였고, 넷 다 `실시간` 이었다.**

> 📌 **위 화면은 측정 시점(`develop` `00dd851`)의 것이다.** 이후 같은 브랜치에서 문구를
> **`경로 기준` / `거리 추정`** 으로 통일해 `실시간` 이라는 단어는 앱에서 사라졌다(§4).

**원인은 mock 세션의 진단과 정확히 같았다.**

| | 응답 |
|---|---|
| `POST /api/meeting {action:"regions"}` | 키가 `ok, regions` **뿐 — `live` 신호가 없다** |
| `POST /api/midpoint {mode:"time"}` (같은 참가자) | **`live: false`** |

### 🔴 B. 이동시간 추정 모델이 얼마나 틀리나 — ✅ **재현. 그리고 더 나빴다.**

측정 방법: 참가자 5명의 출발지를 **카카오 지오코딩(실키)** 으로 잡고,
구간마다 `/api/route-detail` 을 1콜씩 호출했다. 이 라우트는 `travelMinutesEx` 와
**같은 엔드포인트·같은 파싱**을 타므로 목록에 뜨는 실값과 동일하다.
자차는 같은 방식으로 TMAP 을 탔다.

#### B-1. 대조표 — 앱 실값 · 앱 추정값 · 자차

| 구간 | 직선 km | **앱 ODsay 실값** | 내용 | **앱 추정값** | 추정÷실값 | 앱 TMAP 자차 |
|---|---:|---:|---|---:|---:|---:|
| 왕십리→건대입구역 | 3.7 | **9분** | 지하철 직통 · 1,550원 | 24분 | **2.67배** | — |
| 강남역→홍대입구역 | 11.2 | **40분** | 지하철 직통 · 1,650원 | 60분 | **1.50배** | — |
| 서울역→잠실역 | 12.3 | **38분** | 지하철 환승 1회 · 1,750원 | 65분 | **1.71배** | — |
| 노원역→수원역 | 43.8 | **89분** | 지하철 환승 1회 · 2,450원 | 216분 | **2.43배** | 127분 · 57km |
| 부발역→부천역 | 67.3 | **110분** | 지하철 환승 3회 · 4,450원 | 329분 | **2.99배** | 117분 · 84km |
| 서울역→대전역 | 142.0 | **251분** ⚠️ | **버스 환승 2회** · 요금 없음 | 688분 | 2.74배 | **170분** · 164km |

**읽는 법 세 가지:**

1. **가까울수록 상대오차가 크다.** 왕십리→건대입구는 실제 9분인데 24분이라고 한다(2.7배).
   `estMinutes` 의 고정 가산 6분이 짧은 구간을 지배한다.
2. **멀수록 절대오차가 폭발한다.** 서울↔부산은 **138분 vs 1,583분 — 11.5배, 24시간짜리 오차**다.
   직선거리 모델에 **고속철 개념이 없기 때문**이고, 이건 파라미터를 조정해서 될 문제가 아니다.
3. **자차 추정은 상대적으로 낫다.** 노원→수원 자차 실값 127분에 대해 추정은 94분,
   부발→부천 117분에 91분이다(약 0.75배). 대중교통 모델만 유독 과대하다.

> **발표에서 쓸 문장**: "우리 앱의 대중교통 추정값은 **실제의 1.5~11배**다.
> 수도권 안에서는 1.5~3배로 방향은 맞고, **시외로 나가면 의미가 없다.**
> 그래서 ODsay 실값이 붙었을 때와 아닐 때를 화면이 구분해서 말해야 한다."

⏸ **카카오맵·네이버지도 대조는 미검증이다.** 카카오맵 데스크톱 웹의 길찾기 UI 를
자동화로 완주하지 못했고(입력 바인딩이 안 잡힘), 네이버지도는 이 환경의 정책상 열리지 않는다.
**위 표의 "실제" 자리는 자차(TMAP)로 대신했다.** 사람이 5분이면 채울 수 있는 항목이라
§6 에 확인 절차를 남겼다.

#### B-2. 🔴 **새 발견 — ODsay 실값도 구간에 따라 크게 틀린다**

서울역→대전역에서 ODsay 가 준 경로 **3개 전부**가 이랬다:

```
[0] 251분  pathType=2  도보3 → 버스(5005) 58분 → 도보2 → 버스(8366) 169분 → 버스(4) 9분
[1] 255분  pathType=2  (같은 앞 구간) → 버스(605) 16분
[2] 255분  pathType=2  (같은 앞 구간) → 버스(201) 13분
```

**KTX 가 하나도 없다.** 요금은 `-1`(정보 없음)이다. 그런데 이 값에 `verified: true` ·
`live: true` 가 붙어 나온다 — **화면은 이걸 실 API 값으로 표시한다**
(측정 당시 라벨 `실시간 4시간 11분`, 문구 통일 후 `경로 기준 4시간 11분`).

같은 ODsay 가, **2.3배 더 먼** 서울역→부산역에는 `pathType 11` 로 **KTX 138분 · 59,800원**을
정확히 준다. 그리고 자차(TMAP)는 대전까지 **170분**이다.

> **즉 "대중교통이 자차보다 81분 느리다"는 값이 실 API 값으로 표시된다.**
> 서울↔대전은 국내에서 고속철이 가장 촘촘한 구간이라, 이 답은 어떤 기준으로도 맞지 않는다.
>
> 🔴 **이건 라벨 문제가 아니다 — 문구를 고쳐도 그대로 남는다.** §4 의 수정은 "추정값에 실값
> 라벨이 붙는 것"을 막지, **ODsay 가 준 값 자체가 틀린 경우**는 막지 못한다.
> 화면은 여전히 `경로 기준 4시간 11분` 이라고 말하고, 그 숫자는 여전히 틀렸다.

⚠️ **`memory/status.md` §3-3 은 이 구간을 "대전 · trafficType 2 · 237분 · `verified: true` →
이미 정상 동작"으로 적어 뒀다. 그 판정을 정정해야 한다.** 파싱은 정상이지만 **값이 틀렸다** —
"우리가 파싱에 성공했다"와 "ODsay 가 맞는 답을 줬다"는 다른 문제다.

⏸ **원인은 미검증**이다. ODsay 가 도시내/도시간 알고리즘을 거리로 가르는데 142km 가
도시내 쪽에 떨어지는 것으로 **보이지만**, 응답만으로는 확정할 수 없다.
`searchPubTransPathT` 의 `SearchPathType` 파라미터를 지정해 보는 것이 다음 실측 과제다.

#### B-3. 접근시간 보정(`odsay-access.ts`)은 동작하지만 과대하다

서울역→부산역 경로 후보:

| | ODsay 값 | 우리가 더한 추정 | 화면 값 |
|---|---:|---:|---:|
| `[0]` KTX (서울역 출발) | 138분 | **+0분** | 138분 |
| `[1]` SRT (수서 출발) | 130분 | **+73분** | 203분 |
| `[2]` KTX | 139분 | **+73분** | 212분 |

- ✅ **출발지가 곧 탑승역이면 0분**을 더한다 — 설계대로 동작한다.
- ⚠️ **서울역→수서역(SRT 탑승역) 접근에 73분**을 매긴다.

  이 73분의 정체는 계산으로 확인했다(💰 0콜): 서울역↔수서역 **직선 13.73km** →
  `estMinutes(13.73, "transit") = 72분`. **응답의 73분과 일치한다** — 즉 접근 구간에도
  §B 가 잰 것과 **똑같은 추정 모델**이 그대로 쓰인다.

  ⏸ 서울역→수서역의 **실제 대중교통 시간은 이 세션에서 재지 않았다.** 다만 §B 에서
  실측한 비슷한 길이의 서울 구간(서울역→잠실역 **12.3km · ODsay 38분 / 추정 65분 · 1.71배**)의
  배율을 그대로 적용하면 **실값은 42분 안팎**으로 짐작된다 → **약 1.7배 과대.**
  `memory/status.md` 의 "약 1.7배 과대" 기록과 **같은 값으로 수렴한다.**

### 🔴 C. 속도 게이트 — 실키에서 몇 초인가 — ✅ **재현. 그리고 더 느려졌다.**

| 조건 | `action=regions` |
|---|---:|
| mock(키 0개) · 4인 — *이전 세션 기록* | 11.29초 |
| **실키 · 4인 · 콜드(캐시 비어 있음)** | **13.87초** |
| 실키 · 4인 · 웜(L1+L2 캐시) | 3.12초 |
| 실키 · 2인 · 프로덕션(`odsay: false`) | 1.55초 |

**계산이 맞는다**: 참가자 4 × 후보 12 = 48쌍, 게이트 간격 250ms → **12초**가 게이트만으로
나온다(`RATE_GAP_MS = 250`). 실 왕복시간은 그 위에 겹쳐 흐른다.

관련 실측:

- **`maxDuration` 선언은 여전히 한 곳도 없다** (`app/`·`lib/`·`next.config.js` 전수 확인).
- **`rateGate()` 호출은 `lib/routing.ts` 한 곳뿐이다** → `/api/route-detail`·`/api/route-path`

원인은 규칙 그 자체다. CLAUDE.md §5 **"실 API 성공값만 캐시한다"** 는 옳은 규칙인데,

> **ODsay 가 못 푸는 참가자가 한 명 있으면, 누군가 화면을 열 때마다
> "후보 수"만큼 실패 호출이 나간다.** 4인 모임 하나를 8번 열었더니 96콜이 나갔다.
> 무료 한도는 1,000콜/일이다 — **모임 하나가 하루 한도의 10%를 태울 수 있다.**

⏸ **실패 호출이 ODsay 무료 한도에 계상되는지는 여전히 미검증**이다
(`memory/status.md` 도 같은 항목을 미검증으로 남겨 뒀다). 계상된다면 이건 비용 결함이고,

키 문제가 아니라 영구적인 사실이다. 둘을 구분할 수 있다(예: `code 3` 은 30분 캐시, HTTP 오류는 캐시 안 함).

## 4. 이 PR 에서 고친 것

프롬프트가 "확정된 결함은 같은 PR 에서 고쳐도 좋다"고 했고, 아래 넷은 **이 세션에서 실측으로
확정한 것**이다. `memory/status.md` §3-0 의 고칠 순서 ①②⑧⑨ 에 해당한다.

### ① `실시간` 배지를 실제 출처에 연결 — **목록 전체가 아니라 사람 단위로**

`RegionCandidate.perParticipant` 항목에 **`real?: boolean`** 을 실었다.

| | 근거 |
|---|---|
| **왜 목록 단위 `live` 가 아닌가** | 화면의 칩이 **참가자 행마다** 붙는다. 그리고 §A-2 실측이 보여주듯 **한 목록 안에 실값과 추정이 섞인다.** 목록 단위 `live` 하나로는 "이 행이 어느 쪽인지" 말할 수 없다 — 전부 `추정값` 으로 내리면 ODsay 실값 3건까지 깎아내린다 |
| **왜 마이그레이션이 없나** | `perParticipant` 는 이미 `meetings.regions` **jsonb 안**에 있다. 스키마 변경 0건 |
| **옛 데이터** | `real === undefined` → **`실시간` 이라고 주장하지 않는다.** 모르면 말하지 않는 쪽이 이 앱의 기준이다(CLAUDE.md §6) |
| 목록 단위 판정이 필요하면 | `perParticipant.every(x => x.real === true)` 로 접는다 |

> 📌 `memory/status.md` 의 PR #28 판단("`live` 는 후보 하나의 속성이 아니라 목록 전체의 속성")과

> **한 사람의 한 숫자가 어디서 왔는지**를 새로 실은 것이다. `travelMinutesEx` 가
> 이미 `{min, real}` 로 돌려주던 값이라 **없던 정보를 만든 게 아니라 버리던 정보를 살렸다.**

lib/tmap.ts    startX · startY · endX · endY · reqCoordType · resCoordType · searchOption
```

**시각 파라미터가 없다.** 그리고 방장이 입력한 모임 시각(`prefs.timeText`·`dateIso`)은
이동시간 계산에 **한 번도 들어가지 않는다** — `routing`·`odsay`·`tmap`·`geo`·`scoring`
전수 검색에서 **0건**이다(타입 `ScoreContext.when` 만 있고 아무도 안 채운다).

> **즉 `실시간` 은 값이 추정일 때만 틀린 게 아니라, 실 API 값일 때도 틀린 이름이었다.**
> §A 가 찾은 것이 ①(추정에도 붙는다)이고, CEO 가 찾은 것이 ②(진짜여도 실시간이 아니다)다.
> **②가 더 근본적이다.**
>
> 앱은 이미 알고 있었다 — 같은 경로 상세 시트가 본문에서는 `시간표 기준` 이라고 적고
> 있었다. **한 화면 안에 모순이 하나 더 있었던 셈이다.**

### 무엇이 바뀌었나

| 자리 | 이전 | 이후 |
|---|---|---|
| 홈 중간지점 카드 | `실 이동시간 기준` / `거리 추정으로 계산` | **`전원 경로 기준` / `일부 거리 추정`** |
| 모임 상세 목록 칩 | `실시간` (조건 없음) | **`경로 기준` / `거리 추정`** (사람 단위) |
| 경로 상세 시트 칩 | `ODsay 실시간` · `TMAP 실시간` / `추정값` | **`경로 기준` / `거리 추정`** |
| 시트 본문 | `시간표 기준` | **`실제 노선으로 계산`** |
| 지도 폴백 | `직선 근사(경로 API 미응답)` | **`거리 추정(실제 경로를 가져오지 못한 구간)`** |
| 홈 결과 카드 | `예상 N분` (출처 없음) | **`경로 기준 N분` / `거리 추정 N분`** |

⚠️ **자차는 사정이 다르다.** TMAP 에도 시각을 안 보내므로 그 값은 **호출한 순간의 도로 상황**이다.
모임은 보통 며칠 뒤라 *신선한데 엉뚱한 시점의 신선함*이다. 그래서 자차 안내를
`지금 출발 기준 · 실시간 교통 반영`(장점처럼 읽힘) → **`지금 출발 기준 — 모임 시각의 도로
상황은 다를 수 있어요`** 로 바꿔 어긋남을 그대로 밝혔다.
